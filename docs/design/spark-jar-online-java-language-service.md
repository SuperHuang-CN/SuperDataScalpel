# Spark JAR 在线 Java 补全与语言服务方案

状态：接入代码已实现，正在真实开发环境验证；尚未完成整体验收，不代表已上线。

记录日期：2026-09-25。适用范围：批处理与实时 Spark JAR 的在线 Java 编辑器。

相关文档：[SDK 与在线开发设计](spark-jar-task-sdk-v1.md)、[Task Engine 编译服务](task-engine-daemon-and-compilation.md)、[本次评估记录](../verification/java-language-service-evaluation-20260925.md)。

## 1. 定位与决策

提供成熟、稳定、实际可用的 Java 代码提示，同时保持轻量在线编辑器定位，不建设完整 IDE 或 Notebook。

确定方向：

- 保留现有 Monaco 编辑器，以 Eclipse JDT LS 提供 Java 语义能力；不自行用正则实现完整 Java 类型系统。
- JDT LS 是独立 Java 进程，不是引入 TaskEngine 同一 JVM 的普通框架依赖。
- 随 TaskEngine 一起交付，由 TaskEngine 管理子进程；开发者启动 TaskEngine 的 `main` 后，不需要再手工启动语言服务。
- **每个独立的活跃编辑工作区使用独立 JDT LS 进程。** 不直接让多个独立编辑会话共享同一个 JDT LS 进程，不修改其内核以实现多用户复用。
- 同一编辑会话的源码同步、补全、诊断持续复用进程，不按每次请求启动进程。
- 保留平台已有的资源名、字段与 SDK 片段提示；接入语言服务不削减现有在线开发、编译、试运行、日志、预览、应用到任务等功能。
- 多人保存同一任务的**版本与冲突处理后续单独讨论**，不纳入本次方案的实施范围。

后续用户已授权实施：语言服务的会话、进程与容量管理放在现有 TaskEngine 中，不新增单独部署服务。
平台侧只承担必要鉴权与转发，沿用现有编辑器。完整测试通过前不将该方案标记为已交付。

## 2. 为什么不采用单进程多人共享

本机实测一个进程可以处理多个 Java 项目的补全请求，响应速度不是唯一问题：

1. A 项目获取候选项，B 项目再发起补全，之后解析 A 原候选项会返回 `Invalid completion proposal`。实测版本的新补全请求会清理进程共享的补全缓存。
2. 工作区符号搜索返回同一工作区内其他项目的类，不提供用户隔离语义。
3. 给请求添加用户 ID、给文件分配不同路径，不能自动解决这些进程级状态问题。

两个独立进程的交错请求对照中，60 次候选解析全部成功，测试的源码诊断与工作区搜索未串扰。详见[评估记录](../verification/java-language-service-evaluation-20260925.md)。

结论是“不采用未经改造的共享进程作为多用户服务”，不是宣称 JDT LS 不支持多项目，也不是断言任何代理改造都不可能。自行管理共享缓存、全局操作和结果过滤不符合当前简单、易维护的目标。

## 3. 工作区与编辑会话

工作区是后台的一套 Java 分析环境：当前源码及未保存修改、依赖 classpath、类型索引、诊断与补全状态。它不等于任务实体，也不等于浏览器窗口。

| 操作 | 预期行为 |
| --- | --- |
| 用户打开一个任务的在线编辑器 | 申请编辑会话，创建或恢复该会话工作区 |
| 同一页面连续输入、请求补全 | 复用原工作区和进程 |
| 同一页面短暂断线 | 在保留期内恢复原会话，不重复创建进程 |
| 页面刷新 | 创建新的独立编辑会话；原会话断连后回收，不承诺恢复未保存源码 |
| 打开另一任务，或另开独立编辑页面 | 默认独立编辑会话，不按用户或任务 ID 自动合并 |
| 两个人打开同一任务、同一脚本 | 独立工作区，未保存内容和语言分析互不覆盖 |
| 关闭页面或连接失效 | 进入断连保留期，到期后回收 |

会话身份由服务端将当前登录用户、任务 ID、编辑页面随机 UUID 组合摘要而成；恢复时重新鉴权。不能仅凭任务 ID 或客户端提供的路径复用进程。同一工作区的重复连接拒绝，不让两个页面同时修改同一分析状态。

**编辑隔离不等于保存冲突保护。** 本文不承诺两个人先后保存或应用同一任务时不会覆盖，也不新增版本锁、合并、占用锁或实时协同机制。原有保存与应用校验保留，后续另行讨论冲突策略。

## 4. 部署与职责

```text
浏览器 Monaco 编辑器
        │ 平台鉴权、源码同步、语言服务消息
        ▼
Admin（鉴权 + 全程 WebSocket 转发）→ TaskEngine
                         │
              ┌──────────┴──────────┐
         TaskEngine A          TaskEngine B
         ├─ 画布预检            ├─ 画布预检
         ├─ Java 编译           ├─ Java 编译
         └─ 会话/进程管理       └─ 会话/进程管理
            ├─ JDT LS 会话 1       └─ JDT LS 会话 3
            └─ JDT LS 会话 2
```

### 4.1 TaskEngine

- 管理语言服务进程的启动、就绪、连接、退出和工作目录回收。
- 分别控制编译容量和语言服务容量，补全资源不足不能耗尽画布预检资源。
- 同部署包、同机器或同容器均可，但 JDT LS 与 TaskEngine 是不同进程；同容器仍共享容器总资源，不代表完整故障隔离。
- 分发包内将 JDT LS 运行目录与 TaskEngine 的 Spark/业务依赖目录分开，不把 Eclipse/OSGi 依赖混入 TaskEngine classpath。
- 优先在现有 TaskEngine 模块完成必要管理代码，不为本需求新增业务 Maven 工程或拆微服务。
- 不将补全交给 Dispatcher 启动任务 Runner，不启动 Spark 数据任务来获取代码提示。

### 4.2 平台与前端

- 沿用现有用户与任务权限；浏览器不持有 TaskEngine 内部认证 Token，不直接访问裸 JDT LS。
- 前端同步当前文档及版本，支持取消过时请求、丢弃过时结果，避免持续输入造成队列堆积。
- Java 语义提示来自 JDT LS，平台资源提示来自已绑定资源元数据，两者在编辑器中合并、去重并按实际上下文展示。
- 分析不读业务数据、不执行用户作业。JDT LS 诊断不替代正式编译及平台任务契约校验。

### 4.3 已确认的通信接入

浏览器先通过已有登录认证向 Admin `POST /api/v1/tasks/{taskId}/java-language-tickets` 申请连接。凭证 30 秒有效、仅一次使用，通过 WebSocket 子协议传递，不放在 URL。随后浏览器连接同一 Admin 的 `/api/v1/java-language/connection`；连接建立后仍由 Admin 全程转发，不要求浏览器直接连接 TaskEngine，不新增 Nginx。

Admin 复用 Spring WebSocket 和 JDK HttpClient；TaskEngine 保留原 JDK HttpServer，增加同进程 Java-WebSocket 内部监听，端口固定为 HTTP 端口加 100（本地 8091 → 8191）。内部连接沿用 TaskEngine Token。JDT LS 每个进程仅使用 stdio，不开额外网络端口。前端使用 vscode-jsonrpc 与 LSP 协议类型，薄适配 Monaco；不引入第二套 UI 框架。

Admin 最长每 15 分钟或登录过期时断开长连接，恢复时重新经过正常登录和任务权限校验。浏览器仅允许同源握手；开发 Vite 代理启用 WebSocket。部署必须让 Admin 访问 TaskEngine HTTP 及 HTTP+100 两个端口；不对浏览器公开内部 Token。

## 5. 会话生命周期与回收

1. **申请**：鉴权、检查容量；优先恢复有效会话，否则创建独立工作区并启动进程。
2. **初始化**：代码区显示明显的“正在准备 Java 开发环境”遮罩，暂不可编辑或插入资源片段；实际补全验证通过并同步当前源码后自动开放编辑，不以 WebSocket 连通或 `ServiceReady` 作为全部就绪依据。
3. **连接中**：持续复用进程；心跳检测连接存活，源码版本用于文档同步，不是任务保存版本机制。
4. **断连保留**：页面关闭、网络断开或心跳失效后进入宽限期；重新鉴权连接成功则恢复。
5. **回收**：保留期结束，先正常关闭语言服务，超时才结束该受管子进程，清理其专属临时目录。
6. **异常恢复**：受管进程失败后，有界重试启动并重新同步源码；连续失败或容量不足时明确提示，不无限重启。

当前默认最多 4 个工作区（包括断连保留中的工作区），每进程最大堆 512 MiB，断连保留 180 秒、每 5 秒扫描回收，初始化最多 120 秒。连接正常但未输入不强制回收。以上是可配置保护值，不是服务器容量承诺。

消息上限 2 MiB，源码上限 256 KiB，工作区输入队列 32 条，Admin 待发送队列 16 条，浏览器同时请求最多 8 个、单请求 15 秒。首次准备失败不自动无限重启，提供重新准备、返回任务定义，以及明确的“暂不使用语义提示，继续编辑”；用户主动降级后仍有资源/SDK 提示。已经就绪的编辑器发生断线时不再锁住正在编辑的代码，自动重连最多 3 次，仍失败时可手动重试。

工作区是可重建的临时分析状态，不是源码权威存储。已保存源码继续存入原任务保存链路；重连优先同步编辑器当前内容，不用旧的已保存源码覆盖本地修改。浏览器关闭或崩溃后的未保存内容恢复能力取决于草稿机制，不能以心跳恢复代替持久化承诺。

回收不得删除已保存源码、当前生效 JAR、任务配置或其他会话目录。TaskEngine 退出时须处理受管进程和遗留工作区，避免孤儿进程；具体崩溃清理需按部署环境验证。

## 6. 容量与多节点

### 6.1 单节点保护

- 设置最大活跃工作区数、同时启动进程数、单进程堆预算和请求等待上限；不能无限创建或排队。
- 容量不足返回明确的资源繁忙状态，编辑和保存仍可使用；不能将静态候选伪装成完整 Java 补全。
- 分别观测进程数、启动耗时、补全延迟、超时/失败率、队列、CPU、进程总内存及回收情况。
- Java 堆上限不等于实际进程内存或容器内存上限。目标环境须给 TaskEngine、语言服务原生内存和操作系统预留空间。
- 本次评估后的初始规划建议是每个活跃工作区约 **1～1.5 GiB 内存预算**，不是固定用量、容量保证或已批准部署配置。

### 6.2 扩容目标

通过新增 TaskEngine 实例并纳入统一入口扩容，平台保持一个服务地址。首次会话可以分配到可用节点，后续文档消息与补全必须回到该会话节点；不能每次请求随机轮询。

- 存量长连接保持节点归属，新会话可分配到新增节点。
- 断线恢复原会话需要节点归属信息；原节点故障时重新分配、初始化并同步源码，不假装无缝迁移内存状态。
- 工作区不跨节点共享可写 Eclipse 目录；各节点保持 JDT LS、Java 与分析依赖版本一致。
- 计划下线时停止接收新会话，再等待或限时释放存量会话。
- 注册中心、Redis、分布式会话存储和 Kubernetes 不是当前默认前提。具体节点归属和反代配置要在多节点接入设计中确定，不能仅写“加反代”视为完成。

现有编译接口也有本地活动请求状态：编译与取消须回到同一节点。现有 HTTP 排队边界、健康/取消请求可达性、上下游超时匹配、超时后工作是否真正退出等问题，需要在相关容量改造中核实解决，不能照搬补全会话路由替代。

TaskEngine 扩容增加的是预检、编译和语言服务容量。实际任务执行仍遵循 Dispatcher/Runner 体系，本文不改变其调度和扩容机制。

## 7. 提示能力与现有功能边界

| 能力 | 方案 |
| --- | --- |
| Java 类型、变量、方法与泛型链式调用补全 | 使用 JDT LS，基于真实源码与 classpath |
| 方法签名、参数提示、悬停说明、导入处理 | 使用成熟语言服务能力，接入后逐项验证 |
| 输入时语法/类型诊断、错误定位 | 在 Monaco 展示，标明来源，与平台编译诊断区分 |
| 模型/JDBC/Kafka 绑定名及已知字段 | 保留平台元数据提示，按资源种类、读写用途与当前上下文筛选 |
| 字符串字段、转换后 Dataset 字段 | 不承诺 Java 类型服务能自动推导；仅对确知字段提示，不臆造结果 |
| 读取、打印、写入等 SDK 片段 | 保留平台快捷插入与既有资源交互 |
| 保存、编译、应用、试运行、日志和输出预览 | 保留现有能力和真实执行边界，不由语言服务取代 |

内网交付需预置并固定兼容的 JDK、Spark、SDK 分析依赖；不依赖用户首次打开页面时联网下载。不能把 Engine Uber JAR 当成用户公开分析 API。语言服务版本、发行包来源、许可证以及源文档资源随实际选型核对；本次评估使用的本机插件版本不自动成为生产固定版本，也不要求生产安装 VS Code。

任务用户源码不因为补全而执行。工程导入、构建脚本、注解处理与依赖下载策略应显式受控，不能默认开启任意工程自动构建来提供补全。

JDT LS 1.60 实测诊断推送不包含可选的文档版本。前端修改时清除旧标记，拒绝明确过期版本以及文档尚未同步时的推送，兼容无版本诊断；后者不能保证严格逐版本对应，最终以“检查代码”的当前源码编译结果为准。

### 补全请求与延迟控制

- 首次初始化握手在前端最多等待 30 秒；同一会话内以临时分析文档验证 `String` 构造器和 SDK `models()` 候选，探测最多 60 秒、每个位置最多 12 次，仅重试不完整结果，无固定倒计时。通过后恢复当前源码并等待一次分析响应（最多 15 秒），随即开放编辑；不额外创建语言进程、预热池或服务，不执行、保存用户作业，也不新增业务接口。首次源码诊断若先于开放编辑到达，保留到就绪后展示。以上是客户端分阶段等待上限，服务端工作区保护值仍保留原配置。
- 文件栏“重命名”在语义服务就绪后开放，使用明确的类名输入与“确认重命名 / 取消”弹窗；失焦不取消或提交。确认使用 JDT 的语义修改同步主类、构造器和当前文件内引用，再由现有源码同步链路更新文件路径与入口展示；包名不变，支持撤销，遵循当前自动/手动保存草稿设置。校验/请求失败就近显示，不静默忽略。编辑器原有符号重命名能力仍保留。
- 入口类定位保留原始 UTF-16 偏移，包括 CRLF 空行；屏蔽注释/字符串时不改变源码长度。TaskEngine 在托管文档路径变化时同步通知 JDT 旧文件删除、新文件创建，避免撤销后复用类名遇到残留资源记录。该通知仅由引擎根据自身文件操作生成，不开放浏览器任意文件操作。
- Spark 4.1.1 通配静态导入可能触发 JDT 1.60 的类型改名兼容问题。仅当当前入口声明的原生改名返回空修改且源码包含该导入时，复用 `documentHighlight` 定位类型引用、层级 `documentSymbol` 定位该类构造器；校验范围与原文、名称冲突，再沿用只读 `actions/check` 检查候选源码。全部通过且缓冲区版本未变才一次性应用；不整理 import、不替换同名变量/字符串/注释、不保存或执行候选代码。不对服务异常、普通符号改名或其他文件修改做替代处理；代码本身有错时兼容路径可能无法改名，保留原文并明确提示。无需新增服务、依赖或 REST 接口。

- 自动触发与连续输入过滤由 Monaco 管理，普通字母使用其原生 `quickSuggestionsDelay: 60` 合并输入，点号等触发字符立即请求；不在 Provider 中另设延迟或按每次文档修改取消补全。Monaco 会在同一单词持续输入时保留请求，并在候选主文本插入后异步解析导入；这两类请求遵循 Monaco 的取消令牌，切换补全上下文时丢弃旧结果。悬停、格式化等其他分析仍校验文档版本。LSP 取消后界面立即停止等待，但服务端未应答的请求仍计入最多 8 个在途请求，避免只取消前端等待而无限堆积。
- 单次请求等待 15 秒后取消，不立即销毁已预热连接；同一请求 60 秒仍未应答才重建失效连接。初始化握手不重置连续失败计数，真正收到分析响应才重置。
- 重连的类型探测及当前源码分析全部通过后也重置连续失败计数，避免只查看代码/文档的空闲用户因多次 15 分钟重新鉴权而耗尽恢复次数。失败初始化尚在退出时不提前消费重试，退出后再安排有界重试；页面销毁取消重试。断线提示按连接关闭码、语义进程通知及失败阶段显示安全原因，不回显内部异常文本、路径或凭证。
- 保留原有 100 项候选上限及 `isIncomplete`，输入更多字符时重新查询，不将截断列表误报为完整结果。显式应用 JDT 常见内部包过滤（`com.sun.*`、`sun.*`、`jdk.*`、`io.micrometer.shaded.*`、`org.graalvm.*`），不改变编译 classpath。缩小到 50 项会影响原有点号方法候选，因此未采用。
- 保留候选完整插入文本、构造参数和自动导入；不启用仅返回占位文本的延迟插入计算，以免用户快速确认时插入不完整调用。方法文档及附加导入仍沿用候选解析链路。
- 初始化握手与首次分析状态分开显示；TaskEngine 缓存并在重连时重放 JDT 的 `ServiceReady` 通知。该通知不等同于所有类型索引已完成；首次补全若返回“空且不完整”，在源码/光标请求未失效时最多再试两次，真正空结果不重试。
- 冷启动建索引仍有成本，不以“已连接”或静态关键字冒充即时语义补全。本机专项耗时与验证边界见 [2026-09-26 优化记录](../verification/java-completion-latency-20260926.md)。
- TaskEngine 在创建工作区目录后只计算一次稳定的文件 URI 前缀；文档 URI 转换和结果 JSON 中的字符串/键匹配只做字符串操作，不按每个候选字段调用 `Path.toUri()`。Windows 的该方法会检查文件系统，重复调用会显著拖慢大候选列表。相对路径仍经过原有白名单校验，编码后的工作目录前缀与目录边界保持不变；这不是缓存分析结果，也不减少候选或诊断。

## 8. 交付配置与验收边界

建议顺序：单工作区端到端接入 → 生命周期与资源上限 → 双用户隔离与失败恢复 → 多节点路由及目标服务器容量验证。

部署使用独立的 Eclipse JDT LS 1.60.0 目录，通过 `DATASCALPEL_JDTLS_HOME` 指定；不依赖开发者的 VS Code 插件，不在打开编辑器时下载。分发包由官方归档校验后预置，版本与 SHA-256 见 TaskEngine 的语言运行时说明。

TaskEngine 环境变量：`DATASCALPEL_LANGUAGE_WORK_ROOT`（默认系统临时目录下 datascalpel-language）、`DATASCALPEL_LANGUAGE_MAX_SESSIONS`（默认 4）、`DATASCALPEL_LANGUAGE_HEAP_MIB`（默认 512）、`DATASCALPEL_LANGUAGE_RETENTION_SECONDS`（默认 180）。关闭语言运行时配置时，原编译、画布和任务执行仍可使用，编辑器明确显示语义服务不可用。

当前落地单 TaskEngine 地址，不宣称已实现自动多节点分配。第 6.2 节是扩容要求；目标服务器容量和多节点路由仍需针对实际部署验证，不增加 Redis、注册中心或独立语言服务。

验证应覆盖候选选择/解析和导入，不只看候选列表能否返回；覆盖不同用户相同任务/包名/类名、刷新重连、容量满、进程崩溃、节点下线和过时诊断。目标服务器上的网络端到端延迟、长时间内存行为和多节点故障恢复尚未验证。本节是后续接入检查范围，不改变根目录关于测试与验证的统一政策。

明确后续再议：任务源码保存版本、多人保存冲突、制品应用冲突和实时协同编辑。不得把“独立工作区互不影响”扩展为“保存同一任务不会冲突”。
