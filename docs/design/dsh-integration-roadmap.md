# DataScalpel 与 DSH 接入路线图

状态：第一阶段已实现并完成单操作者验证；第二阶段独立验证台已实现，运行验收见[第二阶段验证记录](dsh-plugin-phase-two-verification.md)。第三阶段已实现 Admin 接入，验收见[第三阶段验证记录](dsh-plugin-phase-three-verification.md)；第四阶段第一批已完成全局助手抽屉和会话管理，见[验证记录](dsh-plugin-phase-four-verification.md)；第二批业务上下文及结果跳转待设计。

适用范围：以插件机制将独立 Docker 部署的 DeepSeek Harness（后文简称 DSH）接入 DataScalpel。本文只维护阶段目标和已确认的总体方向；实施细节按阶段另行设计。

## 1. 现状与总体方向

DSH 已通过官方 npm 发布包运行在工程维护的 Docker 环境中，用户已在原生页面配置模型、MCP 和 Skills，并初步操作 DataScalpel。当前运行包版本为 `@deepseek-ai/dsh@0.1.5-rc.1`；源码 ZIP 是旧版分析资料，不是部署或开发基线。

已确认的接入方向：

- 多个系统用户共用一个 DSH 实例。
- 每个用户对应一个个人工作区，首次打开系统助手时自动创建；工作区下可以有多个对话。
- DSH 继续负责智能体运行；DataScalpel 承载最终的系统入口和用户身份。
- 扩展优先通过配置、Preset 和插件完成，不修改 DSH 核心或直接修补已安装包。
- 插件源码在本工程 `integrations/dsh-plugin/` 内维护，独立构建和版本管理，不加入 Maven Reactor；源码目录的创建和维护属于开发任务。
- 现有系统 MCP 继续作为智能体操作业务 API 的能力入口，与在线 MCP 开发平台保持独立。

这些是最终接入方向，不表示第一阶段已经实现多用户、自动绑定系统用户或文件隔离。

## 3. 第一阶段的明确边界

第一阶段选择“内部接口与验证脚本”，不扩展 DSH 原生页面，也不开发 DataScalpel 助手页面。

只验证基础对话、原生追问和生命周期，使用一个可信的技术验证操作者及独立的验证工作区。已有模型提供方配置可以复用；验证 Preset 只组装基础对话和原生追问能力，不接入或验证已有 MCP、Skills、业务操作、文件传输和页面联动。现有工作 Preset 及原生使用环境保留。

第一阶段交付应包含工程内源码、安装配置、验证脚本、实际验证记录和限制说明。仅完成文档不等于插件已实现；仅完成基础对话也不能宣称支持多用户。

## 4. 阶段推进与文档维护

最初的文档落地任务仅编写路线图及第一阶段规格。后续“完成第一阶段”任务已交付仓库内插件源码、镜像安装、内部接口与脚本，并在现有 DSH Docker 服务中完成真实对话及重启恢复验证。

第二阶段使用固定测试账号、独立身份 MCP 与受控文件工具验证共享实例。第三阶段在此基础上实现 Admin 用户绑定与系统 MCP 接入；第四阶段第一批已接入顶部全局助手抽屉。

开发和验证遵循[根开发约定](../../AGENTS.md)。本路线图不恢复全工程强制测试要求；实际验收结果在阶段文档中记录，不把计划中的验收项写成已通过。
