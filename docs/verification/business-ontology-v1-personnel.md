# 业务建模 V1 对齐检查与人员模型验证

状态：2026-09-15 开发环境检查。对照用户确认的“当前配置直接保存”计划；本报告不替代该计划，也不将未完成项视为已验收。

## 结论

当前实现可以完成基本建模和真实数据验证，但底层业务建模仍有本报告列出的后续项，不能认定为完整对齐全部 V1。本体总览 V1 已实现并在人员、部门真实配置上完成页面与权限验收。没有建设版本管理、业务数据副本或 Action 执行功能。

## 保留的测试模型

- 人员：`user`，对象类型 UUID `7024196c-f1ff-4fce-9461-6defa03bbe92`。
- 部门：`department`，对象类型 UUID `502f250f-a32f-4000-9ebc-e2591b80dd22`。
- 人员主来源：已发布 `sys_user`，模型 UUID `c0b937e9-3891-4c2b-9de1-8d903258f033`。
- 部门主来源及人员补充来源：已发布 `ods_sys_dept`，模型 UUID `c4ad705a-af66-4170-9dab-93af8d18edc7`，物理表为 `sys_dept`。
- 两个模型当前都在 `DEV-PG-STORE`，属于多模型组合验证，**不是跨 JDBC 数据源验证**。

人员唯一键由可空的 `user_no` 改为主键 `id`（LONG），接口以字符串传输。显示名称使用 `user_name`；`user_no` 保留前导零，不做编码转换。主来源固定筛选 `del_flag = 0`。

| 属性组 | 业务属性 | 来源 |
| --- | --- | --- |
| 身份信息 | 人员标识、员工编号、姓名 | `sys_user.id/user_no/user_name` |
| 组织任职 | 所属部门标识、职位 | `sys_user.dept_id/position` |
| 组织任职 | 部门名称、所属区域 | `sys_dept.dept_name/area_name` |
| 账号状态 | 登录账号、用户类型、允许登录 HR、业务状态 | `sys_user.login_name/user_type/login_flag/status` |
| 备注 | 备注 | `sys_user.remarks` |

共 12 个属性、4 个组。未导入密码、密文密码、头像或全部物理字段。当前样例不纳入联系电话等非必要个人信息。`status` 没有已确认的枚举含义，保留来源原值，不擅自解释为在职／离职。

补充来源按 `sys_user.dept_id = sys_dept.id` 匹配，同时限定部门 `del_flag = 0`；数据时间未配置，展示“未知”。

关系：

1. 人员“所属部门”／部门“部门人员”：多对一，`dept_id → id`。
2. 部门“上级部门”／“下级部门”：同类型多对一自关联，`parent_id → id`。

人员登记“查询人员资料”和“发起资料核查”两个能力，均为**仅定义，未接入执行**。没有调用外部业务接口，没有创建核查单或修改账号权限。
