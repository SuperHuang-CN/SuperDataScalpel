### 原因与影响

`FileDatasetParseJobCoordinator.claimPreparation` 使用
`file-datasets/materialized/{fileId}/{jobId}[.gdb]`，同一个 Job 的多个 attempt 共享前缀。
GDB/SHP 准备器在重试开始、准备异常和过期结果丢弃时按前缀清理，没有按执行尝试隔离。
数据库层的租约校验能够拒绝过期状态提交，却无法保护共享前缀下的新物化对象。

本次 GDB 的具体分支是：旧尝试恢复后 S3 上传失败，prepare 的异常清理删除共用前缀；新尝试发布的
结果因此失去文件。日志还出现不可重复读取上传流的 `mark/reset` 异常，这是本次触发旧尝试失败的
路径，不改变“多个尝试共用清理目标”的核心问题。

这类风险不只存在于手动挂起，还可能由长时间进程停顿或连接阻塞导致的租约过期触发。
正常并发与故障恢复的数据完整性分别验证。

修复采用每次持久化领取递增的 attemptCount 隔离物化前缀；不同尝试与旧版前缀互为兄弟目录，
只发布当前有效租约对应的结果，旧尝试只能清理自己的前缀。无需改表结构或迁移已发布来源。
强制终止造成的未发布尝试目录可能成为孤儿，不在接管时越界清理；仍需人工核对引用后处理。

## 修复及回归

`{jobId}-attempt-{attemptCount}[.gdb]`，不增加表字段、公共 API 或新框架。
