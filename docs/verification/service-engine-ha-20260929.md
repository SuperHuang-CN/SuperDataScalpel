# Service Engine 双节点与 Redis 集群实测（2026-09-29）

本文保留改造前证据；后续实现及验收结果见 [PostgreSQL 轻量多副本修复与验证](service-engine-ha-postgresql-20260929.md)。下文 `run.ps1` 描述的是当时版本，当前脚本已切换到无 Redis 的测试程序，原始程序及结果另有本地备份。

范围：用户授权的隔离验证；不修改业务实现、不调整现有 IDEA 实例、不提交代码。本文区分原配置验证与诊断性绕过，不能把后者视为当前系统开箱支持高可用。

## 环境与方法

- 从当前 IDEA Service Engine 进程提取实际 classpath；测试使用工程当前已编译 Engine 类和实际依赖 JAR，没有重建或替换业务实现。
- API Studio 为 `3.0.0-SNAPSHOT`，被测 JAR SHA-256：`2159524323E1FA92D5BF835179A53D4B31514578AEF0B1E57F81A8BC563DAD2C`。
- JDK 21.0.2、Spring Boot 4.1.0、本地 PostgreSQL 17.4、用户启动的本地 Redis 6379。
- 测试 JVM A/B 仅监听 `127.0.0.1:18081/18082`，共同使用随机新建的 `engine_ha_probe_<时间戳>` 数据库、相同测试 Engine code 和独立 API Studio service-name。数据库只包含生成的三行数据与三类测试服务。
- 未将测试 Engine 登记到 Admin，不访问用户业务表。管理 Token 随机生成，数据库凭据仅从本机已有配置读取到内存及临时配置，不进入报告。
- B 通过测试专用 TCP 转发端口 16380 访问真实 Redis。断链只关闭 B 的测试连接，不关闭、清空或改配用户 Redis。
- 初次探索发现管理 HTTP 端口可早于启动恢复开放；正式复测改为等待 `/actuator/health/readiness` 为 UP 后再开始操作。未使用仅等待端口开放的探索结果判定重启恢复或断链补偿是否通过。

测试程序、每次 JVM 日志及原始 JSON 位于不提交的 `.local/engine-ha/`。`EngineHaProbe.java` 为测试编排程序，`run.ps1` 提取 IDEA classpath 并启动；不是产品代码或正式部署脚本。

## 原始配置的启动阻断

1. 原有运行依赖加 `spring.super-api-studio.cluster-type=redis`：启动失败，`IntegrationAutoConfiguration` 与 `RedisClusterNotifyConfig` 注册同名 `getClusterNotify` Bean，触发 `BeanDefinitionOverrideException`。证据：`result-baseline.json`、`A-redis-1790692493811.log`。
2. 仅在测试配置允许 Bean 覆盖后：继续启动失败，缺少 `org.springframework.data.redis.listener.Topic`。API Studio 的 Redis Starter 是 optional，当前 Engine 实际 classpath 没有 Redis 相关运行依赖。证据：`result-override-only.json`、`A-redis-1790692528616.log`。

为继续判断通知机制本身，后续**仅测试进程**额外添加 Boot 4.1.0 Redis Starter 的依赖，并允许 Bean 覆盖。依赖通过根 Maven Wrapper 及 `settings-superhuang.xml` 解析到临时测试 POM，未修改项目 POM。允许同名覆盖不是建议采用的生产修复方式。

## 正式双节点结果

以下是补齐测试依赖并绕过 Bean 名冲突之后的结果，不代表原始配置通过。

| 操作 | 实测结果 | 判断 |
| --- | --- | --- |
| 测试频道发送配置刷新通知 | Redis 返回 2 个接收者 | 两节点确实接入通知，不是仅设置开关 |
| 只向 A 下发 Engine 白名单 | A 放行、B 403 | Engine 自身访问策略未跨节点刷新 |
| 向 B 重发同一策略版本 | 管理接口成功、业务仍 403 | 数据库相同版本幂等返回未补装 B 的内存策略 |
| B 重启、就绪后访问 | 恢复数据库中的白名单 | 启动恢复存在，不等于运行时同步 |
| A 注册测试数据源 | B 的数据源测试接口 200 | 本次注册链路成功，不代表所有数据源生命周期均已覆盖 |
| A 发布、更新脚本 API | A/B 均 200，脚本版本一致 | 正常在线的 Redis 路由通知链路有效 |
| A 发布、更新 SQL/标准服务 | A 200、B 404 | 自有动态路由未接入 API Studio 集群通知 |
| B 重启、就绪后请求三类服务 | 均加载当前已部署版本，A/B 均 200 | 持久化部署恢复有效 |
| B 加载后，A 再更新 SQL/标准服务 | A/B 均 200，但 SQL 返回 id=3/2，标准服务返回 id=1/2 | 旧版本残留，单看 HTTP 成功率发现不了 |
| B Redis 断链期间，A 更新脚本 v2→v3 | A v3、B v2，均 200 | B 漏掉更新通知 |
| 恢复 B 的 Redis 连接 | 刷新通知接收者恢复为 2；12 秒和 32 秒时 B 仍 v2、A v3 | 在本次观测窗口内没有自动补齐漏掉的 API 更新 |
| 漏通知后重启 B 并等待就绪 | B 恢复为 v3 | 启动全量恢复能修复本次不一致 |
| 强制结束测试 A JVM | 直连 B 的脚本/SQL/标准服务均 200，返回最新测试版本 | B 可独立执行已加载服务；未证明负载均衡器自动切流 |
| A 重启后只向 A 下发拒绝 localhost 的新策略 | A 403，B 仍 200 | 已有白名单的节点同样不会跟随最新拒绝策略 |
| 在 A 卸载脚本服务 | A/B 均 404 | 正常在线的脚本卸载通知有效 |
| 在 A 卸载 SQL/标准服务 | A 404，B 仍 200 并返回数据 | 另一节点残留已停用服务，是安全与生命周期一致性缺口 |
| 卸载后重启 B 并等待就绪 | 三类服务 A/B 均 404 | 数据库中的已移除状态能在重启后恢复一致 |

原始明细包含 HTTP 状态及无敏感信息的测试响应，见 `.local/engine-ha/result.json`。这里的 200 只说明该请求成功，不代表跨节点版本一致；版本字段及固定测试数据才是比对依据。

最终复测使用数据库 `engine_ha_probe_1790692874653`。结束时已关闭全部测试 JVM 与 16380 转发端口、删除所有本轮新建测试数据库及包含凭据的临时节点配置。删除的是可重新生成的测试数据，不可恢复，也没有删除或改动用户数据库。测试源码和日志保留在 `.local/engine-ha/`；原 IDEA Engine 和用户 Redis 保持运行。

## 结论与后续处理边界

作者确实设计了 API Studio 的 Redis 集群通知，而且绕过启动接线问题后，正常在线的脚本发布、更新、卸载链路实际有效。当前 DataScalpel Service Engine **不能只增加实例、打开 Redis 开关就按生产双活运行**：

1. 首先需要正式解决可选依赖和自动配置冲突，不能把全局允许 Bean 覆盖当成最终方案。
2. 标准/SQL 动态路由、Engine 访问策略及部署状态需要统一的多节点一致性机制，不只同步 API Studio 的脚本路由。
3. 需要版本检查及漏通知补偿；Redis 连上、HTTP 健康不表示节点已经执行最新版本。
4. 集群就绪、并发发布/撤回协调、故障切换和入口负载均衡仍需完整验收。

现有数据库持久化及启动恢复可作为单活故障接管的基础，但本次只验证了重启恢复和幸存节点直连，未实现选主、租约或防止旧节点继续运行的隔离机制，不能称为已经具备自动主备高可用。

本次仅验证与记录，不修复以上业务/架构问题。

## 验证边界

- 本轮不是压力测试，未验证长时运行、滚动发布、并发管理命令、数据库/Redis 主备切换。
- 没有部署 Nginx 或其他负载均衡器；直连幸存 B 节点成功，不等于已经验证入口自动切流或在途请求无损。
- 两个实例使用相同 Engine 身份是为检验用户提出的共享数据库多副本方案，不代表当前设计已支持该部署方式。
- 未测试 Admin 多实例，也未改变网关的高可用实现。
