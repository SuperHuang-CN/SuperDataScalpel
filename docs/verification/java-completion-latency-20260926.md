## 实测基线与调整

环境：本机 Java 21.0.2、官方 JDT LS 1.60.0、512 MiB 堆、2 个可见处理器，使用真实隔离工作区及现有 SDK/Spark 分析依赖。

同一源码 `new Strin`，连续请求：

| 场景 | 调整前 | 调整后样本 |
| --- | --- | --- |
| 初始化握手 | 5.14 秒 | 4.42 秒 |
| 首次建索引中的空结果 | 7.17 秒、5.09 秒 | 6.22 秒；下一次 5.51 秒得到候选 |
| 预热后的构造器补全（后 5 次） | 1136、941、962、862、771 ms | 744、997、788、793、685 ms |
| 预热后 `String` 候选 | 存在 | 存在 |

上述为工作区 → JDT → 工作区耗时，不包含浏览器、Admin 转发和 60ms 输入合并等待，不是服务器容量/SLA，也没有证明冷启动显著改善。操作系统缓存、后台负载会影响结果。

调整：保留原有 100 项候选上限，显式设置内部类型过滤、保留未完整列表继续查询；前端取消失效请求、限制在途数量、避免慢请求立即断线、空且不完整结果有限重试。

试验但未采用：缩小到 50 项能达到约 0.4～0.6 秒，但回归发现点号后 `String.trim()` 会被截断，已撤回；延迟插入文本计算收益不明显且会影响快速确认时的完整插入，也未采用。最终改动不宣称延迟减半。

最终保留 100 项后的完整回归重测：握手 4417ms；首次补全 6278ms 返回空且不完整，下一次 3911ms 返回 `String()`；其后 603、564、506、513、530、532ms，`new String().` 方法补全 529ms。两轮 100 项样本有明显波动，不能把其中最小值当成保证。

## 第二轮：TaskEngine URI 转换开销（2026-09-26）

用户反馈预热后仍不够自然，继续定位到 TaskEngine 自身的结果转换：`rewrite` 对 JSON 的每个文本值和对象键重复执行 `project.toUri()`；Windows 下该操作会检查文件系统是否为目录。合成 100 候选的结果转换平均约 340ms，并非 Java 语义计算本身。

修复仅在创建工作目录后计算一次稳定的 URI 前缀；后续收发用字符串转换。保留 100 项候选、真实类型分析、解析导入、诊断、既有 URI 校验与会话隔离，不引入新的服务、依赖或分析结果缓存。
