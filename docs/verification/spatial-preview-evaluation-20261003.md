# 空间预览场景实测记录

2026-10-03。对应[落地方案](../design/model-management.md#spatial-preview-design)。本文是证据记录，实施选择以方案为准。现有业务代码没有修改；实验脚本及派生产物保存在不提交的 `.local/spatial-preview-bench/`。

## 方法与边界

本机 Windows 11、约 64 GiB RAM；Java 21，实验进程 `-Xmx512m`。真实开发应用复用 8080/8887，没有启动临时应用或 Mock。数据库为用户授权的 102 内网实验库，只写入专用测试表；原始文件不修改。JTS/Java2D 图片原型将几何落盘、包络索引驻内存，按范围逐条解码；1024×768、半像素显示处理、默认每幅图 15 秒截止。源准备实验限制 120 秒、WKB 2 GiB，按 5,000 条检查，存在一批的超量；产品方案要求写入前检查。

每个规模连续测试完整范围、宽高为完整范围 10% 的局部、平移后的局部、1% 局部、回到完整范围。除另注外每种规模一个 Java 进程、一次序列；未控制 OS/数据库冷缓存，不是 P95 或并发容量认证。局部以首要素为中心，样本多为前缀，不能代表全图所有位置的最坏情况。阶段合计不含 JVM 启动、HTTP、浏览器和实验专用 SSH 凭据发现。实验未给客户库运行动态 MVT 或全表拓扑简化。

文件主体使用 GDAL/PROJ，GeoParquet 几何读取另外使用项目已有 Java ParquetReader。正式应用的上传、解析、属性接口另行实测，不能把两部分拼接成已经实现的新地图链路。GeoJSON/Lines 的分页原型存在反复扫描前缀，另做顺序读取纠正；不能将低效实验读取器的速度写成格式本身的上限。GDB 大样本也采用分页实验，正式实现选择已有 Cursor 单遍读取，其性能须在实现后核实。

实际失败及解决前提：

- 原始 `ghydv_0108.gdb.zip` 只有根数据库文件，无 `.gdb` 目录，现有准备器明确拒绝“ZIP 中只允许包含一个 .gdb 目录”。实验仅重打包副本，不修改原文件。
- 规范化 GDB 与 `wuhan.zip` 在未明确 EPSG 时解析失败：现有 Reader 未从其 WKT 识别到 EPSG。指定经数据检查确认的 4549 / 4326 后，正式解析及属性预览通过。失败轮次的约 120 秒是脚本轮询上限，不是服务器处理了 120 秒；解析队列有具体失败原因。
- SHP 第一次请求漏传必填 DBF 后备编码导致 400，属于实验请求构造错误，补齐后重测，不作为平台缺陷。
- GeoParquet 实验 Python 扩展下载受网络 TLS 限制，改用项目现成的 Java ParquetReader 完整读取 10 万 WKB；未引入生产依赖。

这些结果说明地图落地必须包括压缩结构适配、空间参考确认和错误恢复，不只是新增一个地图页签。本文上传成功只证明现有解析/属性能力，不代表新增文件地图已经实现。

现有模型 `ghydv` 35 条、EPSG:4549、无空间索引，能力检查通过；PNG 接口 3 个并发实际请求均为 200、35 个要素、无截断，每次约 0.87 秒、105,716 字节。当前接口仍有 5,000 要素/50 万坐标/16 MiB WKB 限制、初始江西范围；此成绩不能用于证明百万表的现有产品能力。

## 结果如何改变方案

采用一条有预算的准备链路、落盘副本、一次生成的全图概览和按范围出图；继续沿用 PNG，取消矢量流协议及每次全表简化。10 万、50 万及百万复杂面有不同的准备时间和密集范围成本，因此需要明确准备状态、缓存概览与细节降级，不能只写一个统一条数阈值或宣传“PNG 支持百万”。

本轮未实施新版 UI、取消调度、共享版本、持久缓存及服务发布流程，因此没有这些新功能的产品联调证据；没有持续多用户压测、完整源库 CPU/IO 剖析或所有投影/非法几何的穷举验证。单次源库查询期间仍有网络和数据库成本，不能声称源库“零压力”。这些不是留给用户选择技术路线的问题，而是按已确定方案实施后的交付验收责任。

另对原始 7,237,697 / 2,321,756 条图层发起全量尝试，实验保护上限为 120 秒、64 MiB 未压缩输出，每 5,000 条检查一次。两者分别在处理到 250,000 / 255,000 条时因输出超限停止，管线耗时 63.93 / 79.02 秒，已有输出约 64.59 / 64.04 MiB；**均未完成全图概览**，部分产物不得作为完整概览或完整块缓存。未运行其余数据，不把样本耗时线性外推为全量实测时间。

文件路径的抽稀阶段约占 17.36 / 17.66 秒；本机读取和转换也有成本。本机处理进程峰值 RSS 约为 155～241 MiB，不包含数据库内存。数据库内抽稀的额外热执行 `EXPLAIN ANALYZE` 约 8.23 / 10.19 秒，使用了 2 个并行 Worker；原始 WKB 查询的额外热执行约 0.11 / 0.25 秒。执行计划不包含客户端网络传输，且与实际游标执行不同，不能当作请求独占 CPU 时间或并发容量证明。原始 WKB 从源库传出约 113 / 118 MiB，说明把抽稀移出数据库仍有读取和网络成本。

本轮为单次串行原型测试，数据库只读已有两张各 10 万条实验表，未读写业务表。文件使用实验用 GDAL/Shapely 路径，不是正式 Java FileGDB Reader；文件已解压，不包含上传、解压、建立空间索引、多级产物、HTTP 或浏览器绘制。数据库管线耗时已扣除实验脚本专用 SSH 凭据发现和连接准备时间；未控制磁盘冷缓存。不同几何库版本会影响简化输出，不能要求两条计算路径字节一致，也不能用这些结果代替正式实现的性能验收。原始分阶段结果、执行计划和报告保留在本机 `.local/spatial-preview-bench/overview/`。

**设计约束修正：不能默认“首次打开便完整扫描并逐要素抽稀，就能迅速得到轻量概览”。** 顶点减少不等于要素数量减少，强简化后的 10 万个面仍可能产生数十 MiB。只有经实测同时满足准备时间与输出预算的来源才走这一方式；小而简单的数据可直接受控显示，不强制预生成概览。需要准备的数据应优先复用文件解析过程，数据库来源则受独立预算约束。下文补充图片路径的受控实验；它验证了小样本的准备和渲染成本，尚未解决完整产品链路和大来源的概览问题。

### 图片路径补充实测

实验复用现有 JTS/Java2D 渲染方式，在 `.local` 中增加屏幕半像素顶点跳过及 STRtree 范围索引；没有修改正式渲染器。每份仅处理前述 10 万条样本，1024×768 透明 PNG，不带属性。文件路径为已解压 GDB → GDAL/PROJ 投影 → WKB 落盘 → Java 索引及渲染；数据库路径为已有实验表 → PostGIS 投影及原始 WKB 内网传输 → 落盘 → 同一 Java 实验程序。数据库只读，禁止并行 Worker，查询超时 15 秒。

| 阶段 | dltb700w 的 10 万条 | JBNTBHTB 的 10 万条 |
| --- | --- | --- |
| 文件读取、投影、WKB 落盘 | 5.79 秒 | 5.17 秒 |
| 文件产物读取解码建索引 / 首次出图 | 0.88 / 1.61 秒 | 0.90 / 1.40 秒 |
| 文件各阶段合计 | 8.28 秒 | 7.47 秒 |
| 数据库查询、投影、内网传输、WKB 落盘 | 3.25 秒 | 7.25 秒 |
| 数据库产物读取解码建索引 / 首次出图 | 0.96 / 1.58 秒 | 1.19 / 2.00 秒 |
| 数据库各阶段合计 | 5.80 秒 | 10.44 秒 |
| 首张 PNG 体积，两条路径一致 | 279 KiB | 426 KiB |
| 已准备数据的局部查询及出图，文件路径两次 | 138 / 83 毫秒 | 553 / 102 毫秒 |
| 已准备数据的局部查询及出图，数据库路径两次 | 202 / 35 毫秒 | 299 / 81 毫秒 |

局部视口宽高分别为样本完整范围的 10%、1%，中心取读取到的第一个要素。数据库无排序，首要素与文件可能不同，因而局部命中数不同，不能据此比较两种来源谁更快。16 次图片输出均未触发实验坐标截断；局部 PNG 约 26～900 KiB。再回完整范围并重新渲染约 0.86～1.10 秒，**并非图片缓存命中**。已人工查看完整样本分布图及局部地块图，尚未完成点线、孔洞、公共边界及全部 CRS 的正确性验收。

上述合计是分阶段计时相加，未包含 JVM 启动和实验专用 SSH 凭据发现约 10 秒，也未包含文件上传、解压、真实 Java 文件解析器、管理接口、HTTP、代理或浏览器合成。因此不能称为端到端首屏时间。100,000 条原始 WKB 仍约 113 / 118 MiB，数据库到应用的首次传输成本仍在；改善的是浏览器传输和后续重复访问，不能宣称消除了源库读取。

额外以内存上限 `-Xmx512m` 串行复跑，两个 Java 进程峰值 RSS 约 522 / 522 MiB，包含 JVM、索引、WKB、临时几何及图片，不能当作纯缓存大小。该轮首图渲染约 2.58 / 2.36 秒，说明受限堆和 GC 也影响时间。**不能将本实验的整份 WKB 驻留内存方案直接上线**；落盘、分批解码方案尚需实施后验证。完整原图层 724 万、232 万条未执行图片准备，不承诺全量可用，不按样本线性推算。

原始脚本、PNG 和结果位于本机 `.local/spatial-preview-bench/overview/`，其中 `raster-database.jsonl`、`raster-file.jsonl`、`raster-memory.json` 分别记录对应轮次。文件处理使用实验依赖，不代表同意引入生产依赖。
