# 实时任务

与一种开发方式配合读取：[Canvas](task-canvas.md) 或 [在线 JAR](task-jar.md)。实时任务持续消费，不能套用批次结束即完成的设计。

## 输入、时间和状态

先确认来源与目标、业务粒度、延迟要求及以下内容：

| 设计项 | 决策与限制 |
| --- | --- |
| 无界来源 | Kafka、JDBC 增量轮询或 TDengine TMQ 等当前支持的来源；记录 Topic/表、起始位置和消费节奏 |
| 静态输入 | `JDBC_INPUT`、`JDBC_QUERY_INPUT` 在实时画布中仍为 `BOUNDED`，启动时作为静态数据使用，不承诺持续刷新；`MODEL_INPUT` 当前仅支持批处理 |
| 事件时间 | 区分业务事件时间、入库时间与处理时间，明确字段类型、时区、空值与异常时间处理 |
| Watermark | 只有能力明确支持时配置；说明迟到容忍度与数据舍弃后果。轮询游标不是 Watermark，设置触发间隔也不会自动产生事件时间语义 |
| 窗口和状态 | 需要窗口、去重或状态处理时说明键、时间边界、状态保留和迟到策略；当前 Canvas 没有通用流式窗口聚合节点，不用批处理 `WINDOW`/`AGGREGATE` 替代 |
| 恢复 | 记录初次启动位置、平台 Checkpoint 管理方式、重启重放与目标重复写入风险；不自行删除或更换 Checkpoint 来“修复”任务 |

`STREAM_JOIN` 当前只支持左侧无界流与右侧有界静态表关联；不支持双流关联。需要现有 Canvas 无法表达的状态计算时，说明选用 JAR 的依据，并按 Spark 公共 API 与当前平台限制设计；不能承诺仅改节点名称就可运行。

当前实时 Canvas 必须且只能有一个无界输入节点，并至少连接一个合法输出；所有输出都需从该输入可达。JDBC 增量输入还限制为一个终端输出节点。这是 Canvas 图限制，不据此臆造 JAR SDK 的同名限制。

## 输出与恢复设计

区分 Spark `append` / `update` / `complete` 输出模式与目标数据库的 `APPEND` / `UPSERT` 写入方式。检查具体算子和 Sink 能否组合，不能只因枚举中存在就认定支持。

- Canvas 的模型/JDBC 输出按微批写入，实时不使用 `OVERWRITE`。重复处理微批可能重复追加；使用 UPSERT 仍需正确的业务键和数据库约束。
- Kafka 输出需要明确消息 key、value 格式、Topic 和下游重复消费影响。
- JAR 的每条持续查询必须经 SDK 注册，使用平台分配的查询名与 Checkpoint；JDBC/模型写入在 `foreachBatch` 中实现适用的批写入逻辑。
- 有状态算法修改、起始位置变更或重放范围扩大可能改变恢复语义，需向用户说明并重新确认设计范围。

不承诺通用 Exactly Once。Checkpoint 能恢复消费进度和状态，不自动为所有外部写入提供事务一致性。实时任务不配置 Cron，也不调用启动/停止接口进行验证。

## 交付判定

Canvas 创建类型为 `SPARK_STREAMING_CANVAS`，编译模式显式为 `STREAMING`；在线 JAR 类型为 `SPARK_STREAMING_JAR`，使用实时入口。

按开发方式完成确认与保存，保持 `DRAFT`。只以最终 Canvas 的 Engine 预校验或最终源码的在线编译为本场景完成条件。交付中区分已检查的结构与未验证的持续消费、迟到处理、恢复、状态规模及真实输出；发布、运行配置调整和业务验收由用户完成。
